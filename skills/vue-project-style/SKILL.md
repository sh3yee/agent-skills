# Vue 项目代码风格

在这个项目中工作时：

## 配合使用的技能

- 处理 Vue 任务时，同时读取并遵循 [vue-best-practices](../vue-best-practices/SKILL.md)。
- 根据当前任务按需读取其他技能：
  - 排查运行错误、警告、响应式或异步问题：[vue-debug-guides](../vue-debug-guides/SKILL.md)。
  - 修改路由、导航守卫或路由参数处理：[vue-router-best-practices](../vue-router-best-practices/SKILL.md)。
  - 修改 Pinia Store 或状态管理逻辑：[vue-pinia-best-practices](../vue-pinia-best-practices/SKILL.md)。
  - 编写、修改或排查测试：[vue-testing-best-practices](../vue-testing-best-practices/SKILL.md)。
  - 创建需要兼容普通值、ref、getter 输入的可复用组合式函数：[create-adaptable-composable](../create-adaptable-composable/SKILL.md)。
  - 修改 JSX / TSX：[vue-jsx-best-practices](../vue-jsx-best-practices/SKILL.md)。
  - 维护明确采用 Options API 的代码：[vue-options-api-best-practices](../vue-options-api-best-practices/SKILL.md)。
- 只加载与当前任务相关的专项技能，不默认加载全部技能；按各技能要求读取必要参考文件，不批量读取无关参考文件。
- 用户明确要求优先。在这些 Vue 技能之间，项目特有的代码风格、命令执行和测试约定以本技能为准，通用 Vue 实践由其他技能补充。
- 专项技能提供实现指导，不代表额外的执行授权；不得据此扩大修改范围、安装依赖、启动或构建程序、运行完整 type-check，或突破本技能的测试与验证约定。

## 核心原则

- 遵循 Less is more：用尽量少的概念、依赖和调用层级表达完整、可靠的工程逻辑。
- 保持简单但不简陋，保持严谨但不过度设计。不能为了快速实现而牺牲职责边界、工程结构、类型安全和可维护性。
- 优先选择直白、易懂、容易维护的实现。不要使用晦涩技巧、聪明但陌生的写法或需要大量注释才能解释的结构。
- 最小改动是减少无关影响，不是回避必要的封装、分层或结构调整。

## 工程结构

- 修改前先确认逻辑应该属于组件、hook、Store、工具函数还是 API 层，并放在职责正确的位置。不要为了方便把代码随意塞进当前文件。
- 让组件、模块和函数只承担清晰且相关的职责。功能增多、职责分叉或出现独立业务语义时，进行合理封装或分层。
- 不要把不同职责持续堆进同一个组件、函数或 Store action，避免形成超大文件和超长方法。
- 根据真实的职责边界和复用需求进行封装。不要为了减少少量重复或追求形式而制造额外抽象。
- 避免用复杂设计模式、注册表、通用框架或晦涩泛型解决简单问题。
- 优先复用项目已有的组件、hook、Store、工具函数、API 封装和样式；只有现有职责不合适时才新增结构。
- 修改已有功能时，检查调用方、数据流、响应式更新、历史记录和持久化等关联影响，不能只修复表面现象。
- 重构时保持现有对外接口和业务行为。需要改变接口、数据结构或调用方式时，先说明影响范围。
- 处理外部数据、跨窗口消息、远程组件和异步接口时，进行必要的类型判断、参数校验、错误处理和状态恢复。
- 对存在多种运行场景或功能开关的模块，优先建立可扩展的能力集合、命令集合或能力矩阵，不要为每个新增能力在表单和业务代码中持续增加独立布尔字段。
- 配置表单可以保存能力状态，但应使用集合、映射或嵌套配置表达；界面展示、用户输入、消息发送和本地执行流程应从统一的能力判断派生，避免只隐藏入口而让绕过入口的操作仍然执行。
- 功能受限时，将限制逻辑放在实际职责边界上，并保持与需求一致；不要为了实现前端行为擅自扩大到后端阻断或其他未授权层级。
- 修改功能时先识别现有模块边界和复用点，把独立业务语义放入合适的组件、hook、Store、服务或工具函数中，避免把临时判断插入无关组件。
- 当同一判断或流程在多个位置出现时，优先提取稳定、语义清晰的共享抽象；新增抽象必须减少耦合或重复，不能为了形式化而制造额外层级。

## 代码风格

- 当前环境是 Windows。生成命令时请使用 PowerShell / Windows 写法，不要生成 Linux/macOS 命令。
- 项目技术栈是 Vue + TypeScript + Naive UI。
- 遵循 Vue 最佳实践，并尊重项目现有结构。
- 局部方法优先使用 `const xxx = () => {}`，事件方法使用 `handleXxx` 命名。
- 优先使用提前返回降低嵌套，使用语义清晰的变量、类型和方法名表达意图。
- 只为关键业务规则、数据边界、兼容处理、异步流程和风险点添加简短中文注释。不要给每个方法写注释，也不要用注释掩盖混乱结构。
- 在 Vue 文件中遵守 Vue `<script setup>` 的职责分区和代码排序规则，尽量保持下面的顺序：
  - imports
  - 类型 / interfaces
  - 常量 const
  - props / emits
  - reactive state / ref
  - computed
  - methods / functions
  - watchers / watchEffect
  - 生命周期钩子和卸载逻辑
- 各类声明和逻辑要集中放置，不要把 methods、computed、watcher、生命周期钩子或其他可执行逻辑交叉插入 state / props / 常量定义区域；如果项目已有明确排序约定，优先遵守项目约定。
- 使用项目现有 Prettier 配置统一格式。
- 除非用户明确要求，不要新增依赖。

## 测试与验证

- 除非用户明确要求编写或保留测试代码，不要在项目中新增或保留测试文件、测试脚本、测试夹具或专门用于测试的业务代码。
- 自行验证时可以运行项目已有测试；需要临时编写测试时，优先放在临时目录，验证结束后删除本次创建的测试文件及产物，不把临时测试代码和命令写入交付代码或文档。
- 不要删除项目原有测试或用户明确要求保留的测试；清理范围仅限本次自行创建的临时测试内容。
## 执行边界

- 不要代替用户安装、升级或卸载项目依赖。需要新增依赖时，只修改项目的依赖声明与必要代码，并在交付时提供由用户执行的安装命令；除非用户在当前请求中明确要求代为安装。
- 不要替用户启动程序，不运行 dev、serve、preview 等启动命令；需要启动时，把命令提供给用户执行。
- 不要替用户 build 程序，不运行 build 等构建命令；需要构建验证时，把命令提供给用户执行。
- 不要主动运行完整 type-check；只有用户在当前请求中明确要求时才运行。
